# ACE-RTL 실제 모델 E2E 검증 실행 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** DeepSeek 모델을 사용하는 기존 ACE-RTL 프로필의 준비·도구 실행·공식 CVDP 평가·후보 선택·보고서를 실제로 검증하고 재현된 프로젝트 문제를 고친다.

**Architecture:** 기존 `scripts/dev.py`의 setup/doctor/smoke/live와 `examples/ace-rtl`의 고정 소스·평가기만 사용한다. 호스트 모델 transport와 Docker OpenCode가 OpenAI 호환 API로 연결되며 호스트 평가기가 Agent 밖에서 과제를 채점한다.

**Tech Stack:** Python 3.12, uv, Docker/Compose, OpenCode 1.18.31, CVDP, DeepSeek OpenAI 호환 API.

**Spec:** `docs/superpowers/specs/2026-09-25-ace-live-e2e-design.md`

## Global Constraints

- 최종 `origin/main`의 접두어 설정인 `AGENT_OPT_MODEL_BASE_URL=https://api.deepseek.com`, `AGENT_OPT_MODEL_ID=deepseek-flash`를 사용한다. `/anthropic`은 사용하지 않는다.
- 키는 실행 중 환경변수로만 전달하며 파일·커밋·로그 출력에 쓰지 않는다. 실제 모델과 mock/합성 fixture 결과를 구분한다.
- ACE/CVDP/HF의 고정 SHA·평가 기준은 바꾸지 않고, private 평가 자료를 Agent에 전달하지 않는다.
- `live --iterations 1`: baseline·후보 × train·validation, 최대 4 trial; 점수 향상을 성공 조건으로 삼지 않는다.
- 기본 디렉토리의 변경사항은 건드리지 않는다. 모든 작업은 `fix/e2e-readiness` 워크트리에서 한다.

### Task 1: 환경 기준선과 공식 평가 준비

**Files:**
- 기존 실행 경로: `scripts/dev.py`, `examples/ace-rtl/environment/setup.py`, `scripts/dev_doctor.py`
- 재현된 프로젝트 오류가 있을 때만 관련 구현과 `tests/test_dev_environment.py` 또는 해당 계약 테스트 수정

**Interfaces:**
- Consumes: 기존 `make setup ARGS="--core"`, `make setup`, `make doctor`, `make smoke` CLI
- Produces: 고정 자산 lock, 실제 이미지/도구 진단과 `runs/dev-smoke-*/summary.json`

- [ ] **Step 1: 코어 기준선.** `make setup ARGS="--core"` 후 `make doctor ARGS="--core --json"`을 실행해 ready·7-trial 합성 데모를 확인한다.
- [ ] **Step 2: 공식 환경 준비.** `make setup`을 실행하고 고정 소스·데이터·driver·이미지 및 `external/setup-logs/`의 실제 결과를 확인한다. 빌드 실패 시 실패 명령과 로그를 먼저 분리하고, 기존 CI의 `apt` 404인지 확인한다.
- [ ] **Step 3: 문제를 재현한 경우에만 수정.** 해당 오류를 드러내는 관련 회귀를 먼저 실행해 실패를 확인하고, 외부 SHA/평가 기준을 바꾸지 않는 최소 변경 후 같은 회귀를 통과시킨다. 외부 저장소의 지속적 404라면 동일 준비 단계를 재시도해 일시적 오류와 프로젝트 문제를 구분한다.
- [ ] **Step 4: 실도구 판정.** `make doctor`, `make smoke`를 실행해 도구 검사·toy 및 공식 CVDP 정답/오답에 실제 nonempty raw tests가 있는지 확인한다. 실패 원인은 같은 방식으로 재현·수정·재검사한다.

### Task 2: 실제 모델과 Agent 실행

**Files:**
- 기존 실행 경로: `src/agent_optimizer/models.py`, `src/agent_optimizer/harnesses/opencode.py`, `examples/ace-rtl/environment/model_checks.py`, `examples/ace-rtl/environment/checks.py`
- 재현된 오류가 있을 때만 관련 구현과 `tests/test_models.py`, `tests/test_adapters.py`, `tests/test_ace_demo.py` 수정

**Interfaces:**
- Consumes: Task 1의 ready lock, 현재 소스에서 다시 빌드한 Docker 이미지, 공개 train/validation manifest와 실행 중 `AGENT_OPT_MODEL_*` 환경
- Produces: 실제 모델 host tool-call, OpenCode 컨테이너 tool-call 및 `runs/dev-live/<id>/`의 평가·보고서

- [ ] **Step 1: 모델 연결.** 키를 파일이나 출력으로 전달하지 않고 현재 실행 프로세스 환경에만 설정한다. `AGENT_OPT_MODEL_BASE_URL`과 `AGENT_OPT_MODEL_ID`를 지정하고 다른 모델 endpoint 변수는 비운다. 기본 브랜치의 모델 설정이나 이미지 플러그인이 바뀌면 `make setup`으로 이미지를 다시 빌드한다. `make doctor ARGS="--model"`을 실행해 호스트 응답 및 컨테이너 도구 호출 결과를 확인한다.
- [ ] **Step 2: 실패 시 경계별 진단.** HTTP 인증·요청 형식, 모델의 tool-call 응답, OpenCode trace, 컨테이너 네트워크를 각각 확인한다. 재현된 코드 문제에만 실패하는 계약 테스트를 먼저 작성하고 수정 후 같은 doctor를 재실행한다.
- [ ] **Step 3: 제한된 live.** `make live ARGS="--iterations 1"`을 실행한다. `runs/dev-live/<id>/summary.json`, `events.jsonl`, `report.html` 및 공식 평가 raw 결과를 대조해 baseline/후보 train·validation, 선택 근거, 실제 완료/실패 상태를 확인한다.
- [ ] **Step 4: 실패 시 재검증.** 원인을 수정할 수 있으면 같은 최대 4-trial 명령을 재실행한다. 환경/인증 등 외부 차단이면 그 단계만 실패로 기록하고 합성·mock 결과로 대체하지 않는다.

### Task 3: 검증 근거와 변경 전달

**Files:**
- Modify: `docs/verification.md` (이번 실행의 날짜별 명령·환경·결과만 추가)
- 관련 회귀: 변경한 모듈의 테스트 파일과 `tests/endpoint-plugin.test.mjs` (endpoint 수정이 있을 때만)

**Interfaces:**
- Consumes: Task 1/2 실행 로그·run id·실제 판정
- Produces: 비밀정보 없는 재현 가능한 검증 기록과 리뷰 가능한 PR

- [ ] **Step 1: 회귀와 결과.** 코드가 변경되었다면 관련 회귀, `make lint`, `make test`, `make demo`를 실행한다. 변경이 없어도 현재 환경에서 `make lint`, `make test`, `make demo`로 기준선을 확인한다. `git diff --check`를 통과시킨다.
- [ ] **Step 2: 사실 기록.** 실제 사용한 명령·Mac/Docker 플랫폼·시험 범위·각 단계 결과·실패 원인을 `docs/verification.md`에 기록한다. 모델 요청 내용과 키, private 평가 자료는 기록하지 않는다.
- [ ] **Step 3: 전달.** `git status`, `git diff`, 최근 커밋을 확인해 의도한 파일만 커밋한다. 작업 브랜치를 푸시하고 `gh pr create`로 PR을 만들며 검증 성공/차단을 PR에 정확히 적는다. 기본 디렉토리의 `main`과 워크트리 상태를 종료 시 확인한다.
