# Generalized optimization report: design

## Goal and boundaries

Make the existing offline experiment report answer whether each Agent × Harness group improved, how its optimizer searched, why its recorded winner was selected, what failed, and what evidence is needed to repeat the run. Preserve existing persisted results and the standalone `report.html` experience. A new optimizer must be able to produce a readable report without modifying HTML renderer code.

The report describes the recorded experiment, not an inferred optimizer success. The minimal demo is a synthetic fixture; the report must preserve that qualification. Scores from distinct Agent × Harness groups or datasets are never ranked as one score. Validation selects a candidate; held-out test is displayed separately and cannot retroactively change that selection.

## Existing evidence and audit

`runner.py` persists schema-v1 `summary.json` (group baseline, stage results, frozen selected validation aggregate, final test), `manifest.json` (experiment, benchmark, budget, objective, source locks), `events.jsonl` (task-level `trial_started`/`trial_completed`, iteration/review/merge events), `candidate.json` (ID, parent IDs, producer, changed files) and `changes.diff` for each candidate. Each trial also has `result.json` and optional harness logs. One trial is one candidate × task × split × repetition execution; one candidate can have many trials and aggregated validation results. An optimizer can create a candidate without ever evaluating it. The final selected row is an aggregate, not a particular trial. Stage checkpoints are optimizer-defined and cannot be interpreted as a common result schema.

Today `html_report.py` and `results.py` independently read raw artifacts. The HTML shows an oversized run ID, four low-priority cards, three repeated score tables, nested panels, a task-time sum that is easily mistaken for whole-run elapsed time, feedback truncated in trial cells, selected-only diff links and incomplete provenance. It omits the experiment name, objective, budget, direct baseline/winner deltas, per-group selection explanation, candidate lineage, failure classification and relevant reproduced configuration. Every table has a 650px minimum width, lacks captions/header scopes and puts verbose heterogeneous metrics in one column. CSS is embedded; there is no JavaScript, filtering or sorting today. Existing `<details>`, standalone CSP, escaping, anchor links, relative diff/artifact links and session index must continue working. The complete baseline suite passed (424 tests, 15 environment-dependent skips) and the minimal run produced seven task-level trials across two groups.

## Approach

Add an additive normalization layer between persisted v1 evidence and output renderers. Keep the runner's existing public result schema, its selection algorithm, all original files, the CLI report command and session index. An explicit `report_schema_version`-tagged `report.json` is a derived artifact, never a replacement for `summary.json` or an alternate selector. Both Markdown and HTML render the same in-memory canonical model; JSON serializes that model. Regeneration always normalizes the authoritative persisted artifacts, rather than trusting a possibly stale derived report.

An in-renderer v1 conversion would perpetuate duplicated calculations. Replacing the runner and optimizer contracts wholesale would impose unnecessary migration costs. The separate normalizer keeps existing optimizers working and gives future optimizers one optional generic metadata contract.

## Canonical model and invariants

`ReportRun` contains identity/status/synthetic qualification, benchmark and objective definitions, budget and reproducibility evidence, observed counts and durations, ordered groups, and ordered events. Each `ReportGroup` is keyed by `(agent_id, harness_id)` and holds its baseline validation aggregate, runner-selected validation aggregate(s), final test aggregates, stages, candidates, evaluations, failures, and optional structure. No cross-group best or improvement exists. The selected aggregate from `summary.json` is authoritative; an individual task evaluation must never be labeled the selected aggregate. If no selection was recorded, the best candidate/evaluation is absent rather than inferred. A missing metric remains unknown, not zero. Direction-sensitive comparison uses the objective's ordered metrics, direction (`maximize`/`minimize`), and aggregate (`mean`/`sum`), without modifying stored scores; a lower-priority lexicographic metric cannot overrule an earlier one. For equal or incomplete metrics, do not claim an unrecorded tie-break reason. Rate percentage-point deltas are shown only for an identified rate metric with comparable validation aggregates; otherwise show raw directional difference with units only when supported.

`Candidate` has a group-qualified ID, recorded parent IDs, producer, changed-file names, available diff/configuration artifact references and optional creation/structure metadata. `Evaluation` represents one recorded task-level trial: its recorded trial ID becomes its evaluation ID, with group/candidate reference, stage, task, split, repetition/seed, status, validity, original metric map, observed timing, feedback, execution details and optional artifacts. A candidate may have zero or multiple evaluations. Separate aggregate rows retain runner-computed objective metrics and trial counts, preventing per-task values from being presented as an aggregate score. Failures are categorized only from explicit status/execution/error evidence: timeout, infrastructure, unsupported/benchmark when explicitly recorded, interrupted, optimizer/run error or scored failure with unconfirmed cause. Unexplained cases remain unknown. Feedback is evidence, not a reliable classifier.

Counts distinguish completed evaluations, passed evaluations, failed evaluations and reserved/incomplete trials when distinguishable from events/summary. `trials_used` remains the runner's budget counter; it is not relabeled as evaluation count. Summed task time is explicitly named a sum, not total run elapsed. New runs may record actual monotonic run wall time as an observed field; legacy runs with no such field show unavailable. No environment, command, git revision, simulator, usage total, score or timestamp is invented when absent.

Normalize legacy `trial_completed` to evaluation entities in file order; use recorded candidate metadata and links only when safe and present. Preserve event order and all original raw data in source artifacts. Corrupt/truncated trailing events cannot erase earlier evidence. Safely bound/escape embedded text and never follow candidate links outside the run. Unknown optimizer names and missing metadata are valid inputs. Model serialization uses JSON-compatible values and a version separate from the experiment and event schema versions.

## Optimizer-independent structure

`structure` consists of optional `kind`, display labels and ordered units. A unit has an ID, parent unit ID (optional), human-readable type/label/ordinal, and references to candidates/evaluations. Candidate-parent edges remain separate so trees and multi-parent merges are representable. Unit kinds are open strings, not a closed algorithm enum: phase, iteration, generation, population, branch, or a plugin-defined unit can coexist. A hierarchy may express phase → iteration → candidate, generation → population member, or branches with multiple parents. Unpopulated dimensions remain absent.

For new runs, the runner records candidate creation and stage boundaries with group identity in the existing event stream, and the optimizer can optionally emit generic, versioned structure-unit events/metadata through `context.emit` (IDs, parent/group unit, label, candidate references). This is additive to the optimizer contract, not a requirement to subclass an adapter. Existing optimizer iteration/merge events can be projected via their common fields, without checking optimizer names; old checkpoints remain inspectable raw data, not guessed hierarchy. Legacy candidates retain their recorded parent edges even when no iteration/group is known. Never assume creation or iteration from candidate ID or numeric trial order. If structure metadata is absent or incomplete, render an event/lineage summary only where evidenced and always fall back to the ordered evaluation table.

Presentation is chosen from structure capabilities (ordered units, parent relations, grouping) rather than optimizer IDs. Small ordered series may use a compact, accessible score strip from real comparable validation aggregates; grouped units use an indented generation/iteration/phase list; branching uses a bounded lineage/tree or best path plus counts; unknown data uses an event list. No chart interpolates absent scores, combines splits or changes recorded order. The canonical evaluation table is always present, even with an enhanced journey.

## Renderer and page design

Place compact experiment identity/status/synthetic indicator and a metadata grid (benchmark and path, objective and direction, budget, optimizer stage names, Agent/Harness groups) at the top. Emphasize only supported common KPIs such as completed evaluations and passed/failed counts; per-group baseline/selected validation comparisons display direction-aware deltas. Where only one group exists, its score may be prominent; when multiple groups exist, show one concise comparison row per group rather than a global best. A separate held-out test view retains the original baseline/winner evidence.

Below comparison: structure-aware optimization journey, always-present evaluation table with numeric alignment and compact failure summaries, selected candidate details per group (recorded selection, objective values, parent/changes, evaluation history and links to snapshot/diff), failure analysis with expandable original feedback/log paths, optimizer stage/checkpoint/observed usage, configuration and reproducibility. Raw optimizer outputs, configuration, candidate metadata and provenance appear under native `<details>`. Candidate files in snapshots are linkable when present and safe; an entire runnable command is shown only if recorded. Selected candidate is never called a best *trial*.

Use a restrained neutral/light palette with OS dark preference, system/monospace fonts, compact table density, a bounded page width, semantic success/warning/error colors, small status labels and no decorative gradients or nested cards. Put important values ahead of metadata; responsive KPI/metadata grids wrap and only tables scroll locally at narrow widths. Long IDs, paths, commands and errors wrap without expanding the document. Use section headings, table captions and scoped headers, visible focus, text statuses and keyboard-accessible `<details>`. Retain standalone HTML with embedded CSS and only small dependency-free JS if needed for progressive-enhancement copy/filter; all core content works without JS. Keep link safety, HTML escaping and the session index intact.

Markdown shows the same per-group baseline/winner/delta, evaluation counts, selected candidate, structure summary, failure evidence and reproducibility as HTML. Both use the canonical model; neither recomputes selection, usage completeness or failure counts. Existing Markdown usage caveats and links to source artifacts remain available. `report.json` exposes this display-ready normalized evidence for downstream tools; no consumer is forced to migrate immediately.

## Compatibility and failure handling

Original schema-v1 summary, manifest, event, candidate and trial artifacts remain readable, and old runs can be regenerated through `agent-opt report RUN --html`. The existing CLI output shape, CSV export, relative links, run-session index and basic artifacts remain valid. Old runs missing candidate metadata or manifest data still get a report with explicit unknowns. Report generation during run failure/interrupt must preserve inspectability; report assembly must not choose a winner or suppress a recorded error. Incremental metadata/event additions must not expose private test feedback to an optimizer; report generation operates on already persisted run evidence after the runner's existing boundaries.

Verify the Markdown, HTML and JSON outputs agree on counts, selected aggregates, score comparisons and provenance without synthetic values. Preserve existing report/CLI, lifecycle, security and usage tests.

Run the full unit suite and lint; generate fresh minimal and failure-oriented reports; regenerate one legacy run. Inspect the actual standalone HTML in a browser at 1440, 1024 and 768px for hierarchy, overflow, detail toggles, links and error readability. Verify the documented limitations: trial budget is not the number of finished evaluations, task-time sum is not run elapsed, an unevaluated candidate has no performance claim, and stage-local optimizer decisions are not rewritten as final validation selection.
