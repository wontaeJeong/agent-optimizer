# 데이터셋 병렬 실행과 터미널 진행 화면 설계

## 목표와 범위

`agent-opt run-session`과 이를 호출하는 `agent-opt tui`에서 선택한 여러 데이터셋을 동시에 실행한다. TTY에서는 각 데이터셋의 대기·실행 중·완료·실패, 현재 단계/과제, 경과 시간을 한 화면에 표시한다. 리다이렉트된 stderr에는 데이터셋을 식별할 수 있는 줄 단위 진행 내역을 남기고 stdout의 최종 JSON은 유지한다. 실행 결과는 데이터셋별 독립 보고서와 session index에 연결한다.

한 PR에서 (1) 데이터셋 병렬화와 진행 화면, (2) 다른 순차 구간의 실행 시간 측정 및 병목 우선순위 기록 순으로 진행한다. Agent×Harness 그룹, stage, 단일 후보의 과제/반복 평가는 이번 변경에서 병렬화하지 않는다. 단일 `agent-opt run`의 평가 계약과 점수 선택도 유지한다.

## 검토한 방법

1. **데이터셋별 별도 프로세스(선택):** 기존 `run_experiment`를 각 프로세스에서 독립 Registry/예산/이벤트 저장소로 실행한다. 플러그인 import 및 전역 상태의 간섭을 피하고 자원 동시 사용을 `--jobs`로 제한할 수 있다. 자식 이벤트를 부모의 표시기로 전달해야 한다.
2. 스레드: 구현량은 작지만 파일 플러그인 import의 `sys.modules`와 사용자 구현의 전역 상태가 공유되어 격리 근거가 부족하다.
3. 모든 그룹·과제·stage까지 병렬화: 단일 데이터셋에도 효과가 있을 수 있으나 공유 예산, 후보 cache, stage-local 이력, 선택/시험 순서와 기록 일관성을 함께 재설계해야 한다. 측정 전에 범위를 넓히지 않는다.

## 데이터 흐름과 실행 계약

- CLI `run-session SESSION [--jobs N]`은 기본값 2, 양의 정수만 허용한다. 실제 실행 수는 데이터셋 수와 `N` 중 작은 값이다. TUI에서 여러 데이터셋을 고르면 같은 기본 병렬 경로로 진입한다.
- 부모는 기존 session v1 입력과 순서를 유지한다. 각 데이터셋은 고유한 `session_root/runs/<순번>/` 아래에 자체 run 디렉터리를 작성한다. 중복 데이터셋 이름도 순번으로 구별하고, 결과/인덱스 배열은 완료 순서가 아닌 원래 입력 순서로 정렬한다.
- 자식 프로세스는 `load_experiment` → `run_experiment(spec, Registry(), output, on_event=...)`를 수행하고, 최소 진행 필드(이벤트 이름, timestamp, dataset, stage, task, phase, iteration, 상태, 소요 시간)만 부모로 보낸다. 원본 이벤트의 feedback, private 평가 자료, 자격증명은 전달하거나 화면에 출력하지 않는다. 전체 이벤트/결과는 기존처럼 각 run의 `events.jsonl`과 보고서에 저장한다.
- 부모는 한 곳에서 진행 이벤트를 소비해 화면을 갱신한다. TTY는 각 데이터셋의 고정 행과 공통 완료/실행/대기 집계를 갱신하고, 비TTY는 식별자를 붙인 시작·전환·완료 줄을 쓴다. `max_trials`는 계획된 평가 수가 아닌 예산 상한으로 표시하며 미확정 ETA를 만들지 않는다. 상태 메시지는 한국어 기본/영어 선택 규칙을 따른다.
- 데이터셋마다 현재 run 완료/실패를 결과로 수집한다. 하나가 실패해도 나머지를 실행하고, 실패한 run의 보고서가 생성되었다면 그 경로를 index에 남긴다. 세션 요약의 `completed`/`partial` 및 exit code 0/3, stdout의 단일 JSON 형태를 유지한다. 워커 프로세스의 예기치 못한 종료도 해당 항목의 오류로 반영한다.
- Ctrl+C에서는 새 작업 예약을 중단하고 실행 중 워커를 종료/정리한다. 이미 작성된 run 산출물을 버리지 않으며 세션이 완료인 것처럼 보고하지 않는다. 워커의 표준 출력과 오류 출력은 최종 JSON이나 Rich 진행 행을 오염시키지 않도록 데이터셋별 로그로 격리한다.

## 측정과 검증

- 기존 `run_wall_time_seconds`, `stage_wall_time_seconds`, `task_wall_time_seconds`, 이벤트 timestamp와 세션 전체 경과 시간을 사용한다. 합성 fixture에서 한 데이터셋만 실행한 시간, 두 데이터셋 순차/병렬 시간, 과제·Agent 실행·평가 시간 비중을 기록한다. 모델/API·Docker 실환경 성능으로 일반화하지 않는다.
- 코드상 다른 순차 경계는 `cli.py`의 데이터셋 준비, `runner.py`의 Agent×Harness 그룹·stage·과제/반복 루프, Optimizer 내부의 이전 결과 의존 반복이다. 측정 근거와 다음 우선순위를 검증 문서에 적고, 실환경 실행을 하지 않았다면 명시한다.
- 테스트는 두 워커의 중첩 실행 증명, `--jobs=1` 순차 보장/잘못된 값 거부, 입력 순서/동명 데이터셋/실패 분리, TTY 동시 행과 비TTY 로그, stdout JSON 불변, 인터럽트 정리 및 보고서 보존을 확인한다. 준비된 코어 환경 전체 테스트와 lint, 최소 데모도 실행한다.
- 실제 CLI/TUI 사용 전·후 터미널 화면을 캡처해 PR 본문에 넣고 캡처 명령·환경·합성 입력 여부를 적는다. 캡처할 수 없는 경우 이유를 기록한다.
