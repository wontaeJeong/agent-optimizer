# Agent Optimizer: research optimizers and end-user CLI/TUI

Date: 2026-09-24. Status: design approved in conversation; implementation and external-model verification pending.

## Product and success criteria

An Agent author supplies a local source directory or pinned Git revision, the Agent's argv execution contract and editable text paths. The application recommends compatible, prepared evaluation datasets and a harness, asks the interactive user to confirm, generates a reproducible experiment, executes one or more of three independent optimizers, displays live progress, and writes a self-contained `report.html`. A non-interactive command supplies the same decisions as flags. A user-supplied dataset and evaluator remain first-class choices. The product core stays domain-independent; RTL assets and tooling belong to example/integration code.

This is **one integrated delivery**: GEPA, Meta-Harness, Ecdysis, data preparation, CLI/TUI, progress, and HTML work together rather than presenting algorithm names as unavailable slots. Successful tests with local fixtures establish contracts, not actual model performance. At least one small real Agent/evaluator run per supported benchmark and algorithm is required before claiming those integrations work in that environment; record missing credentials or tools explicitly.

## User journey and configuration

1. `agent-opt init` opens an interactive wizard on a TTY; `agent-opt init --agent ... --argv ... --editable ... --dataset ... --optimizer ...` offers a non-interactive equivalent. Guide source pinning, Agent execution command, output contract, editable text paths, dataset, model configuration, budgets and selected optimizers. Suggest safe defaults but show the resolved plan and require confirmation before downloads or execution. Never infer a working Agent command or scoring rule merely from README text.
2. Detect compatibility from declared Agent capabilities and dataset metadata; recommend CVDP only for a supported RTL task form, Verilog-Eval only for supported generation/completion output form, and a supplied benchmark when its evaluator is registered. Unrecognized or ambiguous cases present choices with explanations. In non-TTY mode require explicit selection when ambiguous and give an actionable error. Credentials come only from environment/credential store; no secret in saved plans or reports.
3. `agent-opt datasets list|prepare` exposes available, cached and unsupported choices, prepares the user's confirmed selection automatically, verifies pins/hashes and reuses intact caches. Offline mode never substitutes or downloads. `agent-opt plan`, `run`, and `report` retain scriptable behavior. `run` accepts a generated or existing experiment. Generated settings and inputs are placed under `runs/configs/<name>/` (Git-ignored, with explicit export for sharing); each run manifest records their hashes and resolved model/dataset/source versions. If multiple compatible benchmarks are selected, run one experiment per benchmark under the same session, with per-dataset progress and linked HTML reports; do not rank scores from different evaluators as if directly comparable.
4. `agent-opt tui` runs the same wizard and live progress view; TTY interactions do not change the underlying experiment semantics. Non-TTY runs print progress to stderr, preserving machine-readable JSON on stdout and the established exit statuses.

## Datasets, evaluation and isolation

- **CVDP:** reuse and extract the reviewed fixed-version downloader/importer and official OSS evaluator currently confined to the ACE example where appropriate, without making the core RTL-specific. Recommend only supported no-commercial task forms. Dataset acquisition may download pinned, hash-checked assets and prepare the matching evaluation environment after confirmation; cache corruption and unsupported tasks fail with diagnostics. Preserve raw official verdicts and environment errors; never silently treat a failed Docker build as a score of zero.
- **Verilog-Eval v2:** fetch the pinned repository into a cache or accept a path that is checked against the expected layout/revision. Import `dataset_spec-to-rtl` and `dataset_code-complete-iccad2023` as distinct task modes. These contain related problems: assign the same problem family to the same split across both modes. Keep public prompt/interface separate from `_test.sv` and `_ref.sv`, and run the testbench only in a private evaluation workspace. The upstream README specifies Icarus v12 and says v13 is unsupported; prepare/verify a separate v12 evaluation runtime instead of reusing CVDP's v13 image. Determine and verify the correct per-task pass/fail protocol against known positive and negative fixtures before enabling live use.
- **Custom dataset:** accept the existing versioned `tasks.json` shape or an explicit import mapping, plus a registered evaluator/argv contract. If there is no reliable scorer, preflight refuses optimization. For unpartitioned input create a deterministic, recorded train/validation/test partition by declared family, with no cross-split family leakage; refuse a partition that lacks enough distinct families for the requested splits. For already partitioned data validate the same boundary. Test is optional only when explicitly chosen; do not imply held-out performance otherwise.
- The runner, not any optimizer, owns trial execution and private data. Optimizers see only train task feedback and bounded public traces, plus validation score vectors needed for candidate selection/frontiers; never test inputs, private reference content, evaluator code, credentials or private file paths. No candidate mutates the original or edits outside `editable`. Preserve `null` for missing usage/metrics, and label partial harness-reported usage separately from complete usage. Meta-Harness and Ecdysis require a declared editable runtime-harness/scaffold surface; an Agent with only a mutable prompt is eligible for GEPA but must not silently receive a mislabeled harness optimization.

## Three independent optimizers

Each implementation fulfills `Optimizer.optimize(context, seeds, config)`, uses `context.propose` for all changes, runs with the same configured Agent/model/data/budget and emits iteration/checkpoint events. Implement genuine search behavior rather than aliasing the existing `simple_feedback` plugin. Register implemented algorithms in `Registry`, retain team-owned file plugins for additional methods and handle model failure/budget exhaustion explicitly.

| Optimizer | Core loop and observable checkpoint |
|---|---|
| GEPA | Evaluate train minibatches, use per-task diagnostic feedback to reflect and mutate editable text, maintain per-task validation performance and a Pareto candidate pool, and support a bounded merge of complementary candidates. Record parentage, evaluated examples, frontier changes and model usage. |
| Meta-Harness | Keep the task model fixed; generate isolated harness/scaffold file candidates using prior train traces and validation evidence, check runnable interfaces, evaluate candidates, maintain a validation frontier and feed its bounded history into the next proposal. Record rejected/invalid proposals and the final candidate. |
| Ecdysis | Collect scored train trajectories, identify failures, group recurring patterns by distinct task IDs (singleton evidence remains secondary), perform configurable multi-pass collaborative failure analysis, propose an isolated edit and retain it only if the fixed train score strictly improves. Record failure groups, specifications and accept/reject decisions. |

The common context needs per-trial train/validation results and an explicit validation-only scoring method; changing it is scoped to these algorithms. Validation may guide within-stage frontier/selection, but test is evaluated only after the runner freezes the final selection. Stage train history remains baseline plus its own candidates; independent stages still start at baseline. An algorithm's internal Pareto set does not silently change the public default final lexicographic `keep=1` across stage winners; explain the two selection levels in the report. Reserve an explicit per-algorithm trial/wall-time allowance and a final-selection/test allowance within the run budget, so an early stage cannot silently starve later stages or final evaluation. Iteration/trial/time caps are enforced; model-call cost is reported only when observed and no unimplemented hard dollar cap is claimed.

## Progress, TUI and HTML

Emit versioned, timestamped lifecycle events for preparation, source resolution, group/stage/iteration, proposal, trial start, Agent execution, evaluation start, trial completion, selection, errors and interruption. Include agent/harness/optimizer, dataset/task/split/repetition, phase, wall-time and trial/iteration counts when available. Avoid private content. The same event stream drives the CLI logger, live terminal view and report; active phase elapsed time is updated locally even during blocking work. Partial runs have durable event logs and a final status.

The terminal view presents the confirmed configuration, current stage/iteration and task, elapsed phase and total time, completed/remaining known work, recent results/errors, and the slowest tasks. Unknown totals stay unknown; don't fabricate ETA. A small wizard and status screen are preferred to a new application framework; screen-reader/plain terminal fallback stays usable.

`report.html` is generated alongside `summary.json`/`report.md`, including on failure or interruption when a run directory exists. Use escaped, local-only assets and bounded rendering of untrusted Agent output/diffs; no CDN or browser fetch needed. Show baseline vs each algorithm/stage and frozen winner, split-aware scores, a timing timeline and slowest tasks/datasets, rejection reasons, provenance/hashes, candidate change links, budget usage and nullable/partial metrics. Mark synthetic data and missing test clearly; preserve JSON/CSV export and Markdown for existing clients.

## Error handling, verification and documentation

Preflight checks compatibility, declared outputs/editable paths, dataset structure/split families, evaluator and model availability, runtime versions, expected asset digests and budget sufficiency before starting an expensive run. Source/asset preparation is atomic and cannot overwrite a valid cache with a partial download. Execution is argv arrays with `shell=False`; subprocess timeouts and interruptions preserve the existing recorded error envelope and produce an inspectable report.
