## Product and success criteria

An Agent author supplies a local source directory or pinned Git revision, the Agent's argv execution contract and editable text paths. The author explicitly selects CVDP, Verilog-Eval or a user-supplied dataset and evaluator; the application then validates compatibility, automatically prepares the selected assets and harness, generates a reproducible experiment, executes one or more of three independent optimizers, displays live progress, and writes a self-contained `report.html`. A non-interactive command supplies the same decisions as flags. The product core stays domain-independent; RTL assets and tooling belong to example/integration code.

This is **one integrated delivery**: GEPA, Meta-Harness, Ecdysis, data preparation, CLI/TUI, progress, and HTML work together rather than presenting algorithm names as unavailable slots. Successful tests with local fixtures establish contracts, not actual model performance. At least one small real Agent/evaluator run per supported benchmark and algorithm is required before claiming those integrations work in that environment; record missing credentials or tools explicitly.

## User journey and configuration

1. `.venv/bin/agent-opt tui` opens the Agent optimization wizard; `agent-opt init --agent ... --command-json ... --editable ... --dataset ... --optimizer ...` is its scriptable equivalent. Guide source pinning, Agent argv, prompt file, editable text paths, explicit dataset selection, evaluator metric/direction, model configuration and trial/wall-time budgets. Show the resolved plan and require confirmation before downloads or execution. Never infer an Agent command or scoring rule from README text.
2. The CLI inventory comes from the central code registry. List CVDP, Verilog-Eval and team datasets without ranking/recommending them. After explicit selection, validate Agent capabilities/evaluator; incompatible pairs fail with an explanation. Non-TTY mode requires `--dataset` before download. Credentials come only from environment/credential store.
3. `make setup ARGS="--dataset <ID>"` or `agent-opt datasets prepare <ID>` prepares only that selected dataset's pinned assets and evaluation runtime. `make doctor ARGS="--dataset <ID> --json"` and `agent-opt doctor --dataset <ID> --json` use the same read-only dataset readiness checks: source/data revision and hashes, imported manifest, runtime/tool version, cached image identity and provider-specific requirements. Doctor never downloads, builds, installs or calls a model. Offline preparation reuses only verified caches and fails on missing assets. Existing `make setup`/`make doctor` continue the existing full ACE environment path; `--core` continues to check/prepare core tooling only.
4. The end user also uses `agent-opt doctor --plan <experiment.toml>` (or a generated plan) before starting an expensive run. It validates the selected Agent source declaration/local pinned-source availability, argv/output/editable contract, central registry IDs, dataset/evaluator readiness, stage options, required binaries/runtime versions, trial budgets, and model endpoint/credential **configuration presence**. It is read-only and does not execute the Agent, optimizer, evaluator, dataset downloads or a model call. `--model` explicitly opts in to the actual model-connectivity probe. Missing inputs produce per-check status, actionable repair command and JSON output; `scripts/dev_doctor.py` consumes the same readiness checks for setup/developer diagnostics.
5. Add one general Agent-optimization entry to the existing numbered development menu. It invokes the same TUI using the prepared `.venv`; the legacy ACE options retain their current behavior. A selected dataset prepares without the ACE OpenCode Agent image unless that dataset provider explicitly requires it. CVDP's new dataset-only setup reuses the pinned driver/data/evaluation image but omits the ACE Agent image. Setup finishes only after selected-dataset doctor checks pass.
6. Generated settings/inputs go under Git-ignored `runs/configs/<name>/` with explicit export. They record the dataset/evaluator/model/source/harness/optimizer IDs and resolved hashes, not a team extension manifest. Multi-dataset sessions run one experiment per evaluator and link separate reports without comparing incompatible scores. Non-TTY progress uses stderr and JSON remains on stdout.

## Team-owned extensibility

Datasets, harnesses and optimizers are expected to grow as a team development responsibility. A single central Python code registry is the supported extension path: a team adds its implementation under `experiments/<team>/` (domain/benchmark code remains in `examples/` when generally shareable) and adds one name→implementation registration in `src/agent_optimizer/registry.py`. There is no `extensions.toml`, runtime scan of arbitrary files, CLI menu edit, or install entry-point change. The registry is the source for `agent-opt plugins`, dataset inventory, wizard choices, setup and doctor. Duplicate IDs are rejected. Existing explicit `experiment.toml [plugins.*]` registrations remain supported for backwards-compatible one-off plugins; they are not the discovery/catalog path for centrally registered team components. The run records selected plugin implementation/helper SHA-256 values for reproducibility.

`DatasetProvider.describe() -> dict` supplies the human-facing name/task form/evaluator ID. `prepare(cache, offline=False) -> dict` returns a pinned public benchmark, evaluator ID/config, and source/data/image provenance; it may fetch/build only when invoked by explicit setup/selection. `doctor(cache) -> structured checks` is read-only: no network access, file mutation, install/build, or model call. `make setup --dataset`, `make doctor --dataset`, `agent-opt datasets prepare`, `agent-opt doctor --dataset`, `agent-opt doctor --plan`, `plugins`, and the TUI all resolve the same central provider/component registration. Missing dependencies, invalid source pins, bad hashes, runtime/version mismatch and unimplemented providers produce component-specific actionable failures. Providers never place private reference/checker assets in Agent workspaces. Team plugins are trusted code, not a sandbox for untrusted packages.

Define one shared `readiness.py` check/result interface in `src/agent_optimizer/` with stable IDs, areas, status/message/repair fields and JSON serialization. It accepts a selected experiment and component registry, asks provider/component checks, and validates plan-level invariants without running trial commands. `scripts/dev_doctor.py` retains host core/network/legacy ACE checks and merges the same dataset readiness checks for `--dataset`; `agent-opt doctor --plan` emits the experiment checks directly. This avoids parallel readiness rules drifting.

Implementation touchpoints: keep the common contracts/runner, replace manifest-based catalog construction with central code registration, update both `scripts/dev.py`/`scripts/bootstrap.sh` setup and `dev_doctor.py`, add a general menu entry that delegates to `agent-opt tui`, and preserve full ACE plus `--core` paths. Tests must prove a Python registry addition is offered through the common inventory, selected setup is followed by read-only doctor, prior CVDP ACE setup still works, and Verilog-Eval v12 requirements appear in doctor. Document this workflow in the dataset template and `docs/adding-components.md`.

## Datasets, evaluation and isolation

- **CVDP:** reuse the reviewed fixed-version downloader/importer and official OSS evaluator. Split selected-dataset setup from full ACE setup: selected CVDP prepares pinned sources/data/driver/evaluation image and its evaluator-only doctor checks; the legacy no-argument full setup continues to prepare ACE's separate OpenCode Agent image as before. Support only reviewed no-commercial task forms. Preserve raw official verdicts and environment errors; never silently treat a failed Docker build as a score of zero.
- **Verilog-Eval v2:** fetch the pinned repository into a cache or accept a path that is checked against the expected layout/revision. Import `dataset_spec-to-rtl` and `dataset_code-complete-iccad2023` as distinct task modes. These contain related problems: assign the same problem family to the same split across both modes. Keep public prompt/interface separate from `_test.sv` and `_ref.sv`, and run the testbench only in a private evaluation workspace. The upstream README specifies Icarus v12 and says v13 is unsupported; prepare/verify a separate v12 evaluation runtime instead of reusing CVDP's v13 image. Determine and verify the correct per-task pass/fail protocol against known positive and negative fixtures before enabling live use.
- **Custom dataset:** accept the existing versioned `tasks.json` shape or an explicit import mapping, plus a registered evaluator/argv contract. If there is no reliable scorer, preflight refuses optimization. For unpartitioned input create a deterministic, recorded train/validation/test partition by declared family, with no cross-split family leakage; refuse a partition that lacks enough distinct families for the requested splits. For already partitioned data validate the same boundary. Test is optional only when explicitly chosen; do not imply held-out performance otherwise.
- The runner, not any optimizer, owns trial execution and private data. Optimizers see only train task feedback and bounded public traces, plus validation score vectors needed for candidate selection/frontiers; never test inputs, private reference content, evaluator code, credentials or private file paths. No candidate mutates the original or edits outside `editable`. Preserve `null` for missing usage/metrics, and label partial harness-reported usage separately from complete usage. Meta-Harness and Ecdysis require a declared editable runtime-harness/scaffold surface; an Agent with only a mutable prompt is eligible for GEPA but must not silently receive a mislabeled harness optimization.

## Three independent optimizers

Each implementation fulfills `Optimizer.optimize(context, seeds, config)`, uses `context.propose` for all changes, runs with the same configured Agent/model/data/budget and emits iteration/checkpoint events. Implement genuine search behavior rather than aliasing the existing `simple_feedback` plugin. Register implemented algorithms in `Registry`, retain team-owned file plugins for additional methods and handle model failure/budget exhaustion explicitly.

| Optimizer | Core loop and observable checkpoint |
|---|---|
| GEPA | Evaluate train minibatches, use per-task diagnostic feedback to reflect and mutate editable text, maintain per-task validation performance and a Pareto candidate pool, and support a bounded merge of complementary candidates. Record parentage, evaluated examples, frontier changes and model usage. |
| Meta-Harness | Keep the task model fixed; generate isolated harness/scaffold file candidates using prior train traces and validation evidence, check runnable interfaces, evaluate candidates, maintain a validation frontier and feed its bounded history into the next proposal. Record rejected/invalid proposals and the final candidate. |
| Ecdysis | Collect scored train trajectories, identify failures, group recurring patterns by distinct task IDs (singleton evidence remains secondary), perform configurable multi-pass collaborative failure analysis, propose an isolated edit and retain it only if the fixed train score strictly improves. Record failure groups, specifications and accept/reject decisions. |

The common context needs per-trial train/validation results and an explicit validation-only scoring method; changing it is scoped to these algorithms. Validation may guide within-stage frontier/selection, but test is evaluated only after the runner freezes the final selection. Stage train history remains baseline plus its own candidates; independent stages still start at baseline. An algorithm's internal Pareto set does not silently change the public default final lexicographic `keep=1` across stage winners; explain the two selection levels in the report. Reserve an explicit per-algorithm trial/wall-time allowance and a final-selection/test allowance within the run budget, so an early stage cannot silently starve later stages or final evaluation. Iteration/trial/time caps are enforced; model-call cost is reported only when observed and no unimplemented hard dollar cap is claimed.

## Progress, TUI and HTML

Emit versioned, timestamped lifecycle events for preparation, source resolution, group/stage/iteration, proposal, trial start, Agent execution, evaluation start, trial completion, selection, errors and interruption. Include agent/harness/optimizer, dataset/task/split/repetition, phase, wall-time and trial/iteration counts when available. Avoid private content. The same event stream drives the CLI logger, live terminal view and report; active phase elapsed time is updated locally even during blocking work. Partial runs have durable event logs and a final status.

The terminal view presents the confirmed configuration, current stage/iteration and task, elapsed phase and total time, completed/remaining known work, recent results/errors, and the slowest tasks. Unknown totals stay unknown; don't fabricate ETA. A small wizard and status screen are preferred to a new application framework; screen-reader/plain terminal fallback stays usable.

`report.html` is generated alongside `summary.json`/`report.md`, including on failure or interruption when a run directory exists. Use escaped, local-only assets and bounded rendering of untrusted Agent output/diffs; no CDN or browser fetch needed. Show baseline vs each algorithm/stage and frozen winner, split-aware scores, a timing timeline and slowest tasks/datasets, rejection reasons, provenance/hashes, candidate change links, budget usage and nullable/partial metrics. Mark synthetic data and missing test clearly; preserve JSON/CSV export and Markdown for existing clients.

## Error handling, verification and documentation

Preflight checks compatibility, declared outputs/editable paths, dataset structure/split families, evaluator and model availability, runtime versions, expected asset digests and budget sufficiency before starting an expensive run. Source/asset preparation is atomic and cannot overwrite a valid cache with a partial download. Execution is argv arrays with `shell=False`; subprocess timeouts and interruptions preserve the existing recorded error envelope and produce an inspectable report.
